## How the UI language works

| Piece | Where |
| --- | --- |
| Library | `next-intl`, plugin `createNextIntlPlugin('./i18n.ts')` in `next.config.ts` |
| Request config | `i18n.ts` loads `messages/{locale}.json` for the 23 codes above |
| Resolution | Cookie `fixtray_locale` wins; otherwise `PlatformConfig.defaultLanguage`; otherwise `en`. Rules are in `src/lib/locale.ts` |
| Provider | `src/app/layout.tsx` (`NextIntlClientProvider`, `<html lang>`) |
| Signed-out control | Dropdown in `src/app/auth/layout.tsx` (top right). Replaces the earlier EN/ES buttons |
| Signed-in control | Same dropdown inside the profile menu (`src/components/TopNavBar.tsx`) and the mobile drawer (`src/components/MobileShell.tsx`). There is no separate top-right language control once someone is signed in |
| Platform default | Super Admin → Global Settings and Admin → System Settings. Both selects list `SUPPORTED_LOCALES` with `LOCALE_LABELS`. Persisted on `PlatformConfig.defaultLanguage` |

Every role uses that same path. Customer, technician, shop owner, and manager shells mount `TopNavBar` (profile menu) and `MobileShell` (drawer). Admin home and admin profile use the same `LanguageSwitcher` in their profile menu. Super admin desktop uses `SuperAdminNavigation`'s profile menu, and the super admin profile page shows the same control. Mobile shells for admin and super admin use `MobileShell`. All of those render one `LanguageSwitcher`, which writes `fixtray_locale` and refreshes. There is no per-role cookie, catalog, or language API. Admin and super admin default-language options are the same `SUPPORTED_LOCALES` list, so adding a code there updates both selects.

Choosing a language writes the cookie and calls `router.refresh()`. Pages then render the matching catalog. There is no runtime DOM walk and no per-character or live AI overlay.

If a catalog file is missing, still being written, or fails to parse, `i18n.ts` loads English instead of returning a 500. `scripts/generate-locale-catalogs.mjs` also copies `messages/en.json` into any missing locale file before translation starts. A missing translation key is logged and the key is shown; it does not crash the page.

Two catalog styles share the same JSON files:

- Named keys (`chrome`, `login`, and the older `common` / `auth` / `workorders` / … skeleton) via `useTranslations`.
- English source strings via `usePhrase()` (`src/lib/usePhrase.ts`). The helper looks the English text up in `src/lib/phraseIndex.json` and reads `phrases.<key>` from the active catalog. Next-intl cannot use a sentence as a key because `.` is nesting, so keys are slugs from `src/lib/phraseKey.ts`.

`scripts/generate-locale-catalogs.mjs` scans `say('…')` literals and nearby label fields, merges them into `messages/en.json`, and writes the other 22 catalogs. Translations are generated once and committed. Existing Spanish strings that were already in `messages/es.json` are kept. Brand tokens (`FixTray`, `DVI`, `ZIP`, `SMS`, `DTC`, `KPI`, `MRR`) are shielded so they are not translated. The cache file `messages/.translation-cache.json` is gitignored. Georgian and the added Indian catalogs are produced by that same script.

## Why the language option disappeared

1. `next-intl` and the English/Spanish catalogs arrived in `60e5cbb` and were never connected. No page called `useTranslations`. The root layout hardcoded `lang="en"`. `i18n.ts` imported `../messages/...`, which points outside the repo.
2. The only language control was Super Admin → Global Settings → Default Language (`75ad5bb`: English, Spanish, French). The June snapshot dropped French.
3. That dropdown did not stick. `PlatformConfig` had no `defaultLanguage` column, and `PUT /api/admin/settings` ignored the field. After Save, the form snapped back to English.
4. Admin → System Settings never had a language field.
5. `FEATURE_MULTI_LANGUAGE` is not what hid the control. Nothing in the UI reads it.

## Messaging auto-translate

Not implemented, and not part of this pass.

- `DirectMessage` stores `body` only. There is no source language or translation field.
- `GET`/`POST /api/messages` read and write that body as-is.
- Account models have no preferred language. The browser cookie cannot tell the server which language a recipient wants while they are offline.
- There is no translation provider in the app. Catalog generation is a build script, not a message pipeline.

## What is wired in this branch

Visible copy in client screens goes through `say()` (`usePhrase`) or `useTranslations`. `scripts/wrap-ui-phrases.mjs` walks JSX text, placeholders, labels, titles, empty states, and button copy. `scripts/generate-locale-catalogs.mjs` writes that English into all 23 catalogs. The dropdown is unchanged: top right when signed out, profile menu and mobile drawer when signed in. Customer, tech, shop/owner, manager, admin, and super admin all reach it from that shared shell.

Covered on purpose for day-to-day use:

- Sign-in, create-account, and password reset
- Shop, tech, and manager home pages, including stats, quick actions, and empty states
- Work-order screens: detail (`/workorders/[id]`), new in-shop and roadside jobs, estimates, cards, and the work-order form
- Shop, tech, and manager settings forms (not only the default-language field), plus admin system settings and superadmin settings
- Role navigation, mobile shell, sidebar, and profile menu
- Messaging chrome (filters, empty state, composer). Message bodies are not translated

The same pass also wraps the other client pages under `src/app` and shared components under `src/components` (customer, admin, and superadmin tools included).

## What is still English

- Email templates and outbound email copy
- Sender-to-receiver message body translation (`DirectMessage.body` is stored and shown as written)
- Sentences built with template literals (counts, names, money) because they are not stable catalog keys. The fixed words around them are catalogued when they were separate JSX text
- API error text that is not also a `say("…")` literal in the UI
- Field names, status codes, and comparison strings that the product uses as data (`licensePlate`, `Paid`, `shopId required`). Those stay English so filters and saves keep working. The label next to the field is translated
- Right-to-left layout for Arabic and Urdu
- A few server-only routes (layouts, legal pages that are not client components) if they have no `say()` call
