# FixTray internationalization

This note records what exists for UI language and messaging translation, why the language control looked gone, and what this change restores.

## UI translation

| Piece | Where | State |
| --- | --- | --- |
| Library | `next-intl` in `package.json`, wired by `createNextIntlPlugin('./i18n.ts')` in `next.config.ts` | Installed since the June 2026 snapshot |
| Request config | `i18n.ts` | Loads `messages/en.json` or `messages/es.json` |
| Catalogs | `messages/en.json`, `messages/es.json` | Shared skeleton (`common`, `auth`, `workorders`, `dashboard`, `admin`, `errors`, `validation`) plus `chrome` and `login` |
| Provider | `src/app/layout.tsx` | `NextIntlClientProvider`; `<html lang>` follows the active locale |
| User choice | Cookie `fixtray_locale` | Set by `src/components/LanguageSwitcher.tsx` |
| Platform default | `PlatformConfig.defaultLanguage` | English or Spanish. Read when the cookie is absent |
| Switcher | Sign-in pages (`src/app/auth/layout.tsx`), profile menu (`src/components/TopNavBar.tsx`), mobile drawer (`src/components/MobileShell.tsx`) | EN/ES on sign-in; English / Español in menus |
| Admin controls | `src/app/superadmin/settings/page.tsx`, `src/app/admin/system-settings/page.tsx` | Default language for people who have not chosen one |
| Feature flag | `multi_language` in `src/lib/featureFlags.ts` (`FEATURE_MULTI_LANGUAGE`) | Not consulted by the UI. Leaving it off does not hide the switcher |

Locale rules live in `src/lib/locale.ts`. A browser cookie overrides the platform default. Unknown codes fall back to English.

Strings that change with the switcher today:

- Sign-in heading, tabs, username, password, and the reset link (`login` keys in `LoginClient`)
- Profile menu: My Profile, clock in/out, mobile view, sign out
- Mobile drawer: language control, switch to web view, sign out

The rest of the product (work orders, shop tools, signup form, emails) is still hardcoded English. The older catalog keys are not referenced by those pages.

## Why the language option disappeared

Git history does not show a user-facing language picker that was later deleted.

1. `next-intl` and the English/Spanish catalogs were added in commit `60e5cbb` ("Restore master code snapshot") and never connected. No page called `useTranslations`. The root layout hardcoded `lang="en"`. `i18n.ts` imported `../messages/...`, which points outside the repo, so the catalogs could not load even if a page asked for them.
2. The only language control was Super Admin → Global Settings → Default Language, added in `75ad5bb` (April 2026) with English, Spanish, and French. The June snapshot dropped French (there is no `messages/fr.json`) and left English/Spanish.
3. That dropdown did not stick. `PlatformConfig` had no `defaultLanguage` column, and `PUT /api/admin/settings` ignored the field. After Save, the response replaced the form and the select snapped back to English.
4. Admin → System Settings (`/admin/system-settings`, where `/admin/settings` redirects) never had a language field.
5. `FEATURE_MULTI_LANGUAGE` defaults to off and nothing in the UI reads `multi_language`, so the flag was not what hid the control.

## Messaging auto-translate

Not implemented. Nothing to reconnect.

- `DirectMessage` (`prisma/schema.prisma`) stores `body` only. There is no source language, translation, or detected-language field.
- `GET`/`POST /api/messages` (`src/app/api/messages/route.ts`) read and write that body as-is.
- Customer, tech, shop, and admin models have no preferred language.
- There is no translation client, provider env var, or detect-language helper.
- `docs/VERSION_0.0.5.md` lists multi-language support as a future item, not a finished feature.

The UI cookie is per browser. It does not tell the server which language a recipient wants while they are offline, so it is not enough to auto-translate a message at send time.

## What this change restores

- Message files load from `./messages/{locale}.json`.
- The sign-in page, desktop profile menu, and mobile drawer show a language control again.
- Choosing a language sets `fixtray_locale` and refreshes the translated chrome above.
- Global Settings and System Settings persist `defaultLanguage` (`en` or `es`). Production adds the column in `src/lib/ensureProductionColumns.ts` because deploys do not always run Prisma migrate. The migration is `prisma/migrations/20260922_platform_config_default_language`.

## What still needs work

Do not treat the switcher as full-product translation.

1. Move hardcoded page copy onto `useTranslations` / `getTranslations`, starting with customer, shop, and tech home screens. Add keys to both `messages/en.json` and `messages/es.json` together.
2. Translate the signup form in `src/components/LoginClient.tsx`. Only the sign-in pane is wired today.
3. Store a preferred locale on each account (customer, tech, shop, admin). The cookie cannot drive messaging.
4. Messaging auto-translate, only after that preference exists:
   - Keep the original `body`.
   - Add `sourceLocale` and a JSON map of locale → translated text on `DirectMessage`.
   - On read, if the recipient's locale differs, call a provider configured with `TRANSLATION_API_KEY` (and a base URL if it is not a hosted SDK). Do not hardcode keys.
   - If the key is missing, return the original text and a status the UI can explain.
   - Show the translation with a control to view the original.
5. French was removed because there is no catalog. Add `messages/fr.json` with the same keys before putting French back on the dropdown.
